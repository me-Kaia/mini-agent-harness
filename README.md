# mini-agent-harness

一个零依赖（纯 Python 标准库）的最小 Agent Harness，用来把 Agent 工程化里最容易出问题的几件事做扎实：
**什么时候停、工具出错怎么办、上下文太长怎么压、崩溃后怎么恢复、效果怎么评测。**

模型接口兼容 OpenAI Chat Completions 格式，可以直接接 DeepSeek API，也可以接本地 llama.cpp server。

## 快速开始

```bash
# 1. 离线单元测试（不需要网络和 API Key）
python -m unittest discover -s tests -v

# 2. 离线评测冒烟（用一个只会算算式的规则"模型"，只验证评测流程能跑通，成功率低是正常的）
python evals/run_eval.py --provider mock

# 3. 接真实模型跑评测（Key 从 --key-env 指定的环境变量读取，默认 LLM_API_KEY，不会打印）
export LLM_API_KEY=你的key
python evals/run_eval.py --provider openai --base-url https://api.deepseek.com --model deepseek-chat

# GSM8K 50 题，每题跑 3 次，统计平均正确率、pass^3、格式遵从率
# 例：Kimi k2.6 非思考模式（temperature/top_p 是平台固定值，传别的会报错；账号限流严，所以加了请求间隔和重试）
python evals/run_eval.py --provider openai --base-url https://api.moonshot.cn/v1 --model kimi-k2.6 \
    --key-env KIMI_API_KEY --tasks evals/gsm8k_50.jsonl --trials 3 \
    --temperature 0.6 --top-p 0.95 --extra-body '{"thinking": {"type": "disabled"}}' \
    --min-interval 3 --max-retries 5

# 只补跑结果文件里调用失败的那几次（同一题、同一次序号），合并到 <原文件名>-rerun.json
# 模型和采样参数沿用原结果，限速和重试用本次命令行的值
python evals/run_eval.py --rerun-errors runs/eval-xxx.json --key-env KIMI_API_KEY --min-interval 10 --max-retries 5

# 接本地 llama.cpp server（llama-server 默认提供 OpenAI 兼容接口）
python evals/run_eval.py --provider openai --base-url http://127.0.0.1:8080/v1 --model local

# 4. 跑单个任务 / 从断点恢复
python main.py "parts.txt 里所有元件的总价是多少？"
python main.py --resume <run_id>
```

## 目录结构

```
harness/
  agent.py          主循环：终止条件、重复调用检测、格式错误计数、每轮存档
  tools.py          工具注册：参数校验、超时、按幂等性重试、输出截断
  context.py        上下文压缩：按"轮次单元"取舍，保证工具调用与结果不被拆开
  state.py          运行状态、原子写存档、JSONL 追踪日志
  llm.py            OpenAI 兼容客户端（429 按 Retry-After 重试、请求限速、额外请求字段）+ 测试用脚本化模型
  builtin_tools.py  示例工具：安全计算器、限定目录的文件读取
evals/              评测任务、评测脚本与判定规则（judge.py）
tests/              84 个单元测试，每个机制都有对应测试
sample_workspace/   评测用的示例文件
```

## 设计取舍

### 1. 终止条件：不只靠最大轮数
主循环有 7 种终止状态：`completed / max_turns / token_budget / timeout / repeated_call / format_errors / llm_error`。

- **最大轮数**只是兜底，等它触发时可能已经白白烧了很多 token。
- **重复调用检测**：把"工具名 + 参数"规范化（JSON 按 key 排序）后算指纹，同一指纹超过 N 次就判定卡住。
  参数顺序不同但语义相同的调用会被识别为同一次。
- **token 预算和耗时上限**直接控制成本，单个异常任务不会拖垮整体。

### 2. 工具容错：先校验、按幂等性决定是否重试
- 模型给的参数不可信。未知工具、非法 JSON、参数类型不对时，**不让工具崩溃，而是把具体错误回灌给模型**，让它自己改。
  这类格式错误**连续**达到上限才终止。
- **格式错误按连续次数计，不按累计次数计**。这个上限要拦的是"模型卡住了、怎么改都改不对"，
  而不是"偶尔出错"。模型出错后看到错误信息、下一次改对了，说明回灌机制正在起作用；如果累计计数，
  一个长任务里零星的几次笔误就会让任务提前终止，等于惩罚了已经纠正的错误。所以只要出现一次格式合法的调用就清零，
  即使这次工具执行失败了（比如超时）也清零：超时是工具的问题，说明模型已经会正确调用。
  真正的死循环（同样的错调用反复出现）另有重复调用检测和最大轮数兜底。
- **只有幂等工具才自动重试**。读文件可以重试；发邮件、写数据库这类有副作用的工具，重试可能导致重复执行，所以默认只执行一次。
- 区分**临时错误**（超时、网络抖动，值得重试）和**确定性错误**（参数错、文件不存在，重试也没用）。
- 工具输出过长时**保留头尾、截掉中间**：日志类输出的关键信息往往在开头（摘要）和结尾（报错）。

### 3. 上下文压缩：以"单元"为最小粒度
上下文超长时要删一部分历史，但**不能把助手发起的工具调用和对应的工具结果拆开**，否则 API 会报错，模型也会读到没头没尾的结果。

做法是先把消息切成单元：一条 assistant 消息 + 紧随其后的所有 tool 消息算一个单元。然后：
- system 消息和第一条用户消息（任务目标）**钉住**，永远保留；
- 最近 K 个单元原样保留；
- 中间的单元压成一条摘要。默认用确定性规则生成（不额外调模型、零成本），也可以传入 `summarizer` 改用模型生成。

### 4. 断点恢复
- 每完成一轮就存一次档，写文件用"先写临时文件再原子替换"，避免写到一半崩溃导致存档损坏。
- 存档点选在"一轮结束"，而不是"工具执行中"：工具执行到一半的状态无法安全恢复。

### 5. 可观测性与评测
- 每次模型调用、工具调用、压缩、终止都写一行 JSONL，记录耗时、token、错误类型、重试次数，方便事后定位"慢在哪""错在哪"。
- 评测脚本统计成功率、平均轮数、平均 token 和终止原因分布，结果存成 JSON，方便对比不同模型或 Prompt 版本。

### 6. 工具安全
- 计算器不用 `eval`，只允许数字和四则运算，防止模型借计算器执行任意代码。
- 文件工具限定在工作目录内，解析 `../` 和符号链接后再检查，防目录穿越。

## 评测结果

2026-11-03 用 DeepSeek（`deepseek-chat`）在 `evals/tasks.jsonl` 的 6 个冒烟任务上跑了评测：
6 个任务全部正常结束（`completed`），全部判定通过，平均 2.5 轮、约 1340 token，
没有触发超时、重复调用或格式错误等终止条件。

| 判定方式 | 成功率 | 说明 |
|---|---|---|
| 旧：关键词子串匹配 | 83%（5/6） | `read_deadline` 回答"2026 年 12 月 15 日"，不包含"2026-12-15"，答对了却被判失败 |
| 新：`evals/judge.py` | 100%（6/6） | 日期统一成 YYYY-MM-DD、数字按完整的数比较后，误判被修正 |

子串匹配还有反方向的问题：`multi_step_cost` 期望"50"，而回答里本来就有"数量 250"，
即使总价算错也可能被判通过。新规则按数值比较，"250"不再算命中；结果文件也改为保存完整回答，
可以确认这次的回答确实是"总价 = 50 元"。两次运行中模型的轮数和回答基本一致，成功率的变化来自判定规则，而不是模型。

**这个评测集很简单，只用于验证评测流程能跑通**，不能说明模型或 harness 在真实任务上的效果。
要区分不同模型或 Prompt，需要加入多步推理、带干扰信息、需要从工具错误中恢复的任务。

### GSM8K 50 题 × 3 次：DeepSeek vs Kimi（2026-11-11）

**为什么 DeepSeek 要重跑。** 2026-11-10 的 DeepSeek 评测用的是 temperature 0.7（结果保留在
[evals/results/](evals/results/) 里，文件名带 `deepseek-t0.7`）。这次接入 Kimi k2.6 时查了官方"模型参数参考"：k2.6 的采样参数是平台固定值，
非思考模式 temperature 固定 0.6、top_p 固定 0.95，传其他值会直接报错。两个模型的采样参数不同就不能直接比，
所以 DeepSeek 按同样的 temperature 0.6、top_p 0.95 重跑了一遍。

| 指标 | DeepSeek t=0.7（旧，仅参考） | DeepSeek t=0.6 | Kimi k2.6 t=0.6 |
|---|---|---|---|
| 模型 / 采样参数 | deepseek-chat，未设 top_p | deepseek-chat，top_p 0.95 | kimi-k2.6 非思考，top_p 0.95 |
| 平均正确率（原始口径） | 96.6% | 95.3% | 97.3% |
| pass^3（原始口径） | 96.0% | 94.0% | 96.0% |
| **平均正确率（修正后，49 题）** | 100.0% | **99.3%** | **99.3%** |
| **pass^3（修正后）** | 100.0% | **98.0%** | **98.0%** |
| 修正后答错 | 0 | 1（gsm8k_161 第 2 次） | 1（gsm8k_209 第 1 次） |
| 格式遵从率 | 100% | 100% | 100% |
| 调用失败（首跑 → 补跑后） | 1（未补跑） | 2 → 0 | 24 → 0（补跑两轮） |
| 平均轮数 | 1.71 | 1.68 | 1.85 |
| 平均 token / 次运行（不可比，见下） | 1005 | 990 | 725 |
| 无重试调用的中位延迟（不可比，见下） | 2.4s | 3.0s | 8.9s |
| 重试次数 / 退避和限速等待 | 未记录 | 1 次 / 19s | 260 次 / 1198s |

结果文件（[evals/results/](evals/results/)）：
- [summary.json](evals/results/summary.json)：三次评测的设置、原始口径和修正后口径的汇总指标、标注修正说明，
  以及每轮补跑了哪几次、用的什么限速设置（`rerun_rounds`）。Kimi 补跑了两轮：第一轮 24 次里 23 次成功，剩下 1 次第二轮补上。
- 每题每次的判定：[DeepSeek t=0.6](evals/results/deepseek-t0.6-verdicts.csv)、
  [Kimi k2.6 t=0.6](evals/results/kimi-k2.6-t0.6-verdicts.csv)、[DeepSeek t=0.7（旧）](evals/results/deepseek-t0.7-verdicts.csv)。
  `rerun` 列为 yes 的是补跑替换进来的结果，`corrected_verdict` 为 excluded 的是修正后口径不计入的题。
- [failures.md](evals/results/failures.md)：三次评测里所有答错（原始口径或修正后口径）的运行，附题目和完整回答。

"无重试调用的中位延迟"和 token 的输入 / 输出拆分来自本地的 trace 日志（`runs/`，不进版本库），没有放进上面的文件。

**怎么读这张表：**
- **准确率上两个模型打平**：修正后都是 99.3% / 98.0%，各错 1 次，且都不是同一题的稳定错误（另外两次都答对了）。
  50 题 × 3 次的样本量下，0.7 和 0.6 的差别（100% vs 99.3%）也只是 1 次运行的差别，不能说明温度有影响。
- **原始口径的差别来自标注问题**：gsm8k_255 题目自相矛盾，DeepSeek 0.6 的 3 次答案是 176、176、96（两次按"20 个牛棚"，
  一次算错），Kimi 3 次都按"10 个牛棚"得 192，正好和标准答案一致，所以 Kimi 原始口径高出 2 个百分点；
  修正后（这题不计入）差距消失。

**token 和延迟不能用来判断谁更省、谁更快。** 表里列出这两项只是记录，不据此下结论：
- **token：tokenizer 差异未核实。** token 数是两家接口各自返回的用量，两家用的 tokenizer 不同。
  Kimi 输入 9.0 万 vs DeepSeek 13.1 万、输出 2.7 万 vs 1.8 万，这个差别有多少来自 tokenizer、多少来自模型行为，没有核实；
  两家单价也不同，token 数不能换算成谁更省。
- **延迟：Kimi 使用未充值账号、存在限流。** Kimi 平台按累计充值金额分级限流，这次用的是未充值账号，
  串行请求、间隔 3 秒仍有大量 429（首跑 16% 的运行重试 5 次后仍失败，改成间隔 10 秒补跑才全部补上）。
  限流状态下的延迟不代表模型本身的速度，DeepSeek 也没有在同等限流条件下测过，所以不比较谁更快。

**耗时口径。** 每次运行的 `seconds` 不含退避和限速等待（单独记在 `wait_seconds`）。但 Kimi 被 429 拒绝的请求本身也要
约 10 秒才返回，这部分仍算在请求时间里，所以表里列的是"没有重试的调用的中位延迟"，平均耗时没有列。
旧的 DeepSeek 结果（0.7 和 0.6 的首跑）是改动前的代码跑的，`seconds` 是墙钟时间、没有重试记录。

**成本（Kimi）。** 实际消耗约 9.0 万输入 token、2.7 万输出 token（含补跑；不含 2 题试跑和中途崩溃的那次首跑），
按 ¥6.5 / ¥27 每百万 token 估算约 ¥1.3。这个单价来自第三方整理，没有在 platform.kimi.com 上核实。

## 已知局限（面试时要能主动说出来）

1. **超时用线程实现，超时后线程仍在后台运行**，Python 线程无法被强制终止。生产环境应把工具放进子进程或沙箱执行，超时直接杀进程。
2. **token 是按字符数粗估的**，不是真实 tokenizer 的结果。
3. **断点恢复时，如果崩溃发生在工具执行中、存档之前**，恢复后这一轮会重跑。有副作用的工具需要自己保证幂等，比如带请求 ID 去重。
4. **压缩无法处理"最近一个单元本身就超长"的情况**，比如单次工具返回了巨量数据。目前靠工具层的输出截断兜底。
5. **评测仍然靠关键词判断对错**。日期会统一成 YYYY-MM-DD、数字按完整的数比较（`evals/judge.py`），
   但"1.2 万""一万二"这类写法、同义表述仍然识别不了。
6. **工具串行执行**，没有并发调用。
7. **模型调用的耗时包含失败尝试本身的时间**：`latency_s` 是各次尝试的请求时间之和（不含退避等待），
   被 429 拒绝的请求如果返回得慢，仍会拉高耗时。更准确的做法是单独记录成功那次请求的时间。

## 可以继续改进的方向

- 用模型生成摘要，替代规则摘要，并对比两种方式的效果和成本
- 评测从关键词匹配升级为"规则 + 模型评判"
- 加入 human-in-the-loop：危险工具执行前要求人工确认，确认超时自动拒绝
- 工具改为子进程执行，实现真正可终止的超时
